Data set

gamebus-gamedb

The few facts about game identity that a launcher cannot work out on its own, and that no upstream project accepts.

What this is

This is not a game database in the catalog sense. It has no genres, no cover art, no release notes, and no ambition to list every game. It collects three narrow kinds of fact:

  • Which store codename belongs to which game. The string a launcher actually has in hand is often not the game's name: an Epic app name, a GOG product id, a directory nobody would recognize.
  • Which executables ship beside many games and therefore can never identify one.
  • Which rows in closed data sets are wrong, where the correction can be stated as a game identity.

Anything a launcher can already derive on its own does not belong here. Neither does anything that belongs in umu-database, the Lutris API, or Discord's detectable list. The scope rule is deliberately narrow, because a data set that collects everything ends up maintained by nobody.

The data set is small and recent: two game pages (Control, Project Hospital) and three helper executables (Unity's crash handlers). It is published in the shape it should keep as it grows, rather than grown first and shaped afterwards.

Why it exists

This knowledge accumulated as a side effect of building a presence daemon, and the obvious thing to do with it was to send it upstream. There is no upstream that takes it.

umu-database
Deliberately scoped to games that require a fix in Proton. That is the first thing their README says, and the umu team confirmed it directly. A correct store codename for a game that already runs fine is out of scope there, and rightly so.
Discord's detectable list
Has no public contribution path at all. A wrong row stays wrong, and everything downstream inherits it.
The Lutris API
Read-only, and it has no field for a store codename. It is where umu sends people who want a broader catalog, but it cannot hold this.

Forking one of those catalogs would mean inheriting maintenance of hundreds of thousands of rows we did not learn, in order to carry the few corrections we did. So the knowledge in between is published on its own, in the shape that makes it reviewable.

What a page looks like

One TOML file per game, with the stores nested inside, because the claim worth reviewing is that these store identities are the same game. This is games/control.toml:

title = "Control"
gamedb = "steam-870780"
note = """
No protonfix exists upstream for this game (checked 2026-08-22), so \
umu-database does not want it and it therefore has no umu id. The Epic \
codename below has nowhere else to go."""

[ids]
steam = 870780
source = "steam-sku"
seen = "2026-08-22"

[[stores.egs]]
codename = "Calluna"
seen = "2026-08-15"
source = "heroic-config"
confidence = "high"
note = "Heroic writes the app name capitalized; Lutris matches it case-sensitively."

Every claim carries how it was learned (source), when (seen), and how sure anyone is (confidence). A reviewer should be able to judge a page without trusting whoever wrote it. TOML was chosen because it is easy to write and format both by hand and by machine, widely understood, and trivially safe to parse anywhere, including on a web page.

One game, one page

Every identifier a page carries is a lookup key that resolves to that page: its canonical id, each store codename, the Steam app id, the umu id, and every executable it names. No two pages may claim the same one, and the validation that runs on every change enforces it.

That rule catches the mistake contributors actually make. Somebody adds a game's GOG copy as a new page, not knowing the Epic copy is already there. Both pages then claim the same identifier, the check fails, and it names both files. The fix is a small human decision: move the store entry onto the existing page. It has to happen before the duplicate lands, because from then on a lookup has two answers and neither is wrong.

Ids

A page's canonical id is derived where an authority already names the game, and minted only where none does: the Steam app id, then the umu id, then a store codename, then an id minted here. The prefix names the namespace the identifier belongs to, and nothing parses the shape of what follows, so gog-1660194629 is a GOG product id and a perfectly good canonical id. Once assigned, an id is frozen. A page that later learns a better identifier records it alongside and keeps the id it had, so nothing that referred to it breaks.

How it is maintained

Contributions arrive as pull requests against a flat directory of pages. No API, no account, no moderation backend: a forge already provides identity, spam control, and continuous integration. A single shared file, which is how comparable data sets usually start, puts every contributor in conflict with the one merged before them. One file per game never does.

A lint validates the whole set on every change: both JSON Schemas, the id rules, and the one-game-one-page rule. It exits non-zero when anything fails, and that exit status is what a merge is gated on. Contributors run the same check locally before opening a pull request.

What is published

The TOML pages are the source of truth. The condensed forms are built from them and published as release assets, never committed, because a binary blob per merge would bloat the repository permanently.

identities.json
Scripts and web pages, and the general case.
identities.parquet
Bulk and analysis. Queryable over HTTP without downloading the whole file first.
identities.sqlite
In-process point lookup, indexed.
shared-helpers.txt
The flat list of helper executables, one basename per line.
manifest.toml
The source commit and a checksum per artifact.

Builds are deterministic: sorted, fixed field order, and no build timestamp inside the data, so a checksum means something and a consumer can tell cheaply whether anything changed. Because the pages are the source of truth, adding a format later or dropping one is a change to the build, never a data migration.

License

The data, meaning the game pages and the helper list, is under the Open Database License v1.0. The lint, the schemas, and the build scripts are code and stay under the project's own code license.

In practice: use it, ship it inside whatever you like, extend it. Nothing here asks you to send changes back to this repository, to ask permission, or to tell anyone you used it. The one thing the license does is keep an enriched copy from disappearing into a product. If you publicly use an adapted version of the database, that adapted version is offered under the same terms. Share-alike attaches to the database, not to the application around it, so a launcher can embed this data in proprietary or GPL code and comply by publishing its extended data set. The attribution the license asks for is a notice, not a credit screen.

None of this is a claim to own facts. A Steam app id belongs to Steam and a store codename to its store, and facts are not copyrightable in any case. What is licensed here is the collection: the selection, the verification, and the notes explaining why an entry says what it says. Protection of that kind is partial and varies by jurisdiction, so the license works here as a norm rather than as a threat.

The rules in full are in README.md, next to the data. The practical path for adding a game is in CONTRIBUTING.md: how to check whether a game is already here, what each field means, how the canonical id is picked, and what the common failures are telling you.
